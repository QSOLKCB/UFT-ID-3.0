# 4. Archive construction

The Zenodo upload surface contains exactly three outer files:

1. UFT-ID-3.0.0-source.zip
2. UFT-ID-v3.0.0-Overview.pdf
3. RELEASE-NOTES.md

The source ZIP is a compound provenance archive. reference-v3.0.0 contains the exact frozen release tree. formal contains the selected verified post-tag Lean layer reconstructed from the LEAN_VERIFIED promotion commit. ARCHIVE-MANIFEST.json records immutable identities and per-file SHA-256 values. SHA256SUMS provides an internal checksum list for the archived reference and formal files.

The ZIP builder normalizes member ordering, timestamps, file modes, compression settings, and JSON serialization. The Overview PDF is generated by a dependency-free deterministic PDF writer with fixed metadata and layout. Release notes are generated after the ZIP and PDF so they can bind both final SHA-256 values without creating a circular self-hash.

Generated ZIP and PDF bytes are publication artifacts, not canonical source files committed to the repository.

# 5. Verification and reproduction

The independent verifier distrusts the archive manifest and checks it against immutable Git objects. It rejects unsafe or non-canonical ZIP paths, directory entries, duplicate member names, unexpected top-level paths, oversized members, non-deterministic timestamps, unexpected modes, malformed checksum rows, manifest identity drift, source-tree drift, formal-layer drift, theorem inventory drift, PDF identity drift, and release-note hash drift.

The reference tree is compared byte-for-byte against git archive output from the frozen v3.0.0 commit. The selected formal layer is compared byte-for-byte against the declared LEAN_VERIFIED promotion commit. The verification record inside the formal layer must still report LEAN_VERIFIED and must bind the expected theorem source blobs.

A deterministic rebuild must reproduce the same source ZIP, Overview PDF, and release notes bytes from the same Git objects and archive contract.

Reproducibility does not upgrade claim scope:
